# Tenant registry records have a schema-by-example contract; instance views are generated

## Context
Developers need concrete per-tenant, per-environment views: endpoints,
resolved products, quotas, version pins. Taxonomy §6 forbids instances in
the model, and instance facts already have owners: structure in the model,
class resolution in bindings, per-tenant facts in the control-plane tenant
registry (KYP-C-FLEET-01) — which so far had no defined record shape.

## Decision
- The tenant registry record shape is defined by example in
  architecture/tenant-registry/example-acme.yaml. Endpoints are keyed by
  KYP-ID, making the KYP-ID the join key across model, bindings and record.
- Developer instance sheets are generated by
  scripts/render_instance_sheet.py, which joins model (export json) x
  bindings x one record for one environment. Sheets are build artifacts:
  never authored by hand, never committed to this repo.

## Consequences
- One authoring surface per fact holds: an endpoint or version change edits
  the registry record only; sheets regenerate.
- The example record is a contract: the real registry implementation and
  the generator both conform to it; changing the shape changes this file
  plus an ADR.
- The repo carries exactly one sample tenant; real records never enter it.

## Rejected alternatives
- Per-tenant modeled views: duplicated subtrees, violates the axes rule.
- Hand-written per-environment wiki pages: guaranteed drift, no single
  authoring surface.
